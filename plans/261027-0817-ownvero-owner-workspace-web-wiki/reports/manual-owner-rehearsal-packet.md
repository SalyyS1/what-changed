# Early owner rehearsal packet

Status: prepared protocol; no participants or completed sessions recorded.

User response, 2026-10-28: no project/participants available yet; keep the real-user
gate open. No request to waive the gate or authorize outreach was made.

## Prerequisites

- Controller verifies a current-source local candidate first. The old installer
  does not contain this workflow. Do not distribute an unapproved binary.
- Owner arranges 3–5 consenting nontechnical app builders. No outreach or contact
  has been initiated by the agent.
- Each person chooses their own test project and two real, bounded changes they
  already want. Use test data and test accounts; never production customer data.
- Explain local storage, manual evidence, clipboard disclosure and the absence of
  an automated runner. Participation may stop at any time. No credential sharing.
- Record consent, candidate/source identity, environment, task wording and the
  participant's anonymous identifier in a private session record. Recordings,
  screenshots and sharing require separate explicit consent.

## Session one: request and review a useful change

1. Ask the owner to explain their app and one behavior that must remain intact.
   They create My app, one capability and a confirmed rule in their own words.
2. They create and save the first real change request, with an example and scope.
   Reopen it to establish persistence.
3. They prepare the Markdown brief, explain included/omitted information and copy
   it only after review. They use their existing coding AI to make the change.
4. They configure a test environment and name the candidate. They author and
   confirm a scenario, then freeze and record a manual observation attempt.
5. Before accepting, ask what was actually checked and what is still unknown.
   They must distinguish owner acceptance from a passed check and an unknown
   deployed build. Do not coach them into a favorable answer.
6. They reject/defer, or explicitly accept with acknowledged exceptions as the
   evidence warrants. Preserve any failure and record one project decision.

## Session two: return for a second real change

After the first change, ask whether they want to use this workflow for their next
planned change. Record refusal as a valid outcome. Do not substitute a reminder or
required exercise for voluntary repeat value.

If they choose to return, they create a separate saved request, preserve the correct
confirmed rules and reuse project memory. Repeat brief → existing coding AI →
manual observations → owner decision. Old evidence must remain historical; it
cannot approve the second candidate. Verify they can export their memory offline.

## Gate and follow-up

Compare every completed session with the phase-06 acceptance criteria. If nobody
can finish without developer interpretation, or nobody values a second cycle,
review the UX/product thesis with the user before P07. Do not mark completion from
the synthetic browser fixture or invent favorable participant quotes.

Clean-Windows runtime packaging and enforceable network-boundary evidence remain
separate mandatory gates. A successful rehearsal cannot waive them.
