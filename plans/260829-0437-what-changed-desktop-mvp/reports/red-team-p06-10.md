## Findings

### F1 — P06's own test commands cannot compile: the synthetic generator is behind gates integration tests do not satisfy  [HIGH]
- **Where:** phase-06-event-engine-queries.md § "Verification Gate" (all four `cargo test` lines) + Requirements: "Synthetic generator (`src-tauri/src/testing/synthetic.rs`, compiled in release only behind the `devtools` cargo feature)"
- **Category:** 6 — verification gate that cannot pass
- **Defect:** P04 declares `src-tauri/src/testing/mod.rs` as "(temp-DB helper, `cfg(test)` + `cfg(feature = "devtools")`)". Integration tests under `src-tauri/tests/` are separate crates: they link the library compiled **without** `cfg(test)`. So `what_changed::testing` — and therefore `testing::synthetic` — does not exist for `tests/query_service.rs`, `tests/cluster.rs`, `tests/importance_calm.rs` or `tests/perf_scale.rs` unless `--features devtools` is passed. None of the four gate commands passes it. The release line is worse: `cargo test --release --test perf_scale` has neither `debug_assertions` nor the feature, so the module the test seeds from is definitively absent.
- **Why it bites:** the implementer writes the generator, runs the phase's own gate, and gets `unresolved import: what_changed::testing` on every listed test. `importance_calm` explicitly needs "a 2,000-event realistic synthetic day" and `perf_scale` needs `seed(profile)`, so there is no partial pass — the whole phase gate fails at compile time, and the natural "fix" (making `testing` unconditionally public) silently ships the generator in release, which is exactly what the phase's own risk row forbids.
- **Fix:** add `--features devtools` to every `cargo test` line in P06's gate, and change the module gate wording to `#[cfg(feature = "devtools")]` alone (drop `debug_assertions` and `cfg(test)` from the *module* gate; keep the double gate on the `simulate_event` **command**). State in P06's Related Code Files that `src/testing/mod.rs`'s gate is narrowed to the feature.

### F2 — the `EXPLAIN QUERY PLAN` criterion is satisfied trivially and cannot detect the missing multi-filter index  [HIGH]
- **Where:** phase-06-event-engine-queries.md Implementation Steps 3: "`EXPLAIN QUERY PLAN` assertions in tests that each filter path uses an index (no `SCAN events`)"; Success Criteria: "`EXPLAIN QUERY PLAN` shows an index for every filter combination the UI can produce (test)"
- **Category:** 6 — verification gate that does not test the claim (plus 5 — index dependency P04 does not create)
- **Defect:** `EventQuery.range` is not optional, so **every** query carries a `timestamp` bound and SQLite will always report `SEARCH events USING INDEX <events(timestamp)> (timestamp>? AND timestamp<?)`. The string `SCAN events` therefore never appears, for any filter combination — including `categories: [a,b,c] + importance_min` combinations that P04's index list (`events(timestamp)`, `(category,timestamp)`, `(entity_id,timestamp)`, `(event_type,timestamp)`, `(importance,timestamp)`) has no composite for, and which SQLite will execute as a range walk with per-row filtering (or an index-per-value loop plus a temp B-tree for the `ORDER BY timestamp DESC, id DESC`).
- **Why it bites:** the assertion passes on day one and keeps passing, so the multi-category + `importance_min` path ships unindexed. It is invisible at the 10k scale P06 measures and only surfaces in P19's 100k/1M gate, after the UI in P07 has been built on those filters. This is the normal path, not an edge case: phase-07's chips are "All / Apps / Windows / Network / Drivers / Files / Development / Docker / Important only", i.e. seven groups over the 15 §9 categories plus an importance filter, so nearly every timeline query is multi-category and several are multi-category **and** `importance_min`.
- **Fix:** replace the "no `SCAN events`" wording with a table of the filter combinations the UI can emit and the **named index expected for each**, assert the plan string contains that index name, and add the composite the multi-filter path needs (e.g. `events(category, importance, timestamp)`) to P04's index list — or state explicitly which combinations are accepted as "range scan + filter" with a rows-examined budget.

### F3 — cluster counts and labels are computed from one page slice inside fixed 60 s buckets, so the user is shown wrong numbers  [MEDIUM]
- **Where:** phase-06-event-engine-queries.md Requirements: "after fetching a keyset page of ≤200 rows, group runs sharing `(category, coarse entity key, 60 s bucket)` with count > 4 into `TimelineItem::Cluster { key, label, count, ... }`"; Success Criteria: "Clustering collapses a 40-event Docker burst into one item and expands back to exactly 40"
- **Category:** 9 — internal contradiction / correctness of a user-visible number
- **Defect:** the count in the label comes from the rows present in the fetched page and from a wall-clock 60 s bucket. A burst that straddles a page boundary yields two clusters with two wrong counts ("25 Docker-related changes" then "15 Docker-related changes"); a burst that straddles a bucket edge (12:00:55 → 12:01:10) splits the same way even inside one page. The phase's risk row only guards set identity ("the union equals the raw set"), which stays true while every displayed count is wrong.
- **Why it bites:** §44's promise is a calm, honest summary line; a split 40-event burst produces two tiles that each understate, and the "expands back to exactly 40" success criterion only passes because the fixture burst happens to fit in one page and one bucket. The test is written to the happy alignment.
- **Fix:** derive `count`, `first_ts`, `last_ts` and `highest_importance` from a bounded aggregate query on the cluster key + window (`SELECT COUNT(*), MIN(ts), MAX(ts) ... WHERE category=? AND entity_key=? AND timestamp BETWEEN ? AND ?`) instead of from the page slice, and replace the fixed 60 s bucket with gap-based run detection (extend a run while the next row is within 60 s). Add a success criterion that a burst straddling both a page edge and a bucket edge still renders one cluster with count 40.

### F4 — `GetTickCount64`-derived boot time is the wrong source for `SinceLastRestart`; the measured probe used a different API  [MEDIUM]
- **Where:** phase-06-event-engine-queries.md Requirements: "`SinceLastRestart` answers a §1 question and resolves from the recorded boot event (falls back to `GetTickCount64`-derived boot time once P13 lands; until then, midnight)"
- **Category:** 1 — API used for something it cannot do
- **Defect:** `GetTickCount64` returns milliseconds since boot **excluding time the system spent suspended**. On any laptop that sleeps, `now - GetTickCount64()` puts "boot" hours or days later than the real boot, silently truncating the "since last restart" window. verified-facts-report.md §2 row 20 measured the correct source instead — "Last boot time | **PASS** | `2026-08-25 00:35:54`" (`Win32_OperatingSystem.LastBootUpTime`, readable non-elevated).
- **Why it bites:** the flagship question "it worked before, what changed?" is answered against a window that starts after the change the user is hunting. The failure is silent — the range simply looks short, and no test in P06 or P13 compares it against a known boot time.
- **Fix:** name the measured source (`LastBootUpTime`, or `NtQuerySystemInformation`/`GetSystemTimeAdjustment`-free equivalent) as the fallback, drop `GetTickCount64`, and add a unit assertion that the resolved boot time equals the recorded boot event's timestamp ±2 s on a machine that has slept.

### F5 — `domain/importance.rs` is created twice  [MEDIUM]
- **Where:** phase-06-event-engine-queries.md Related Code Files: "**Create** — ... `src-tauri/src/domain/importance.rs`" vs phase-04-domain-model-persistence.md Related Code Files: "**Create** — ... `src-tauri/src/domain/{mod.rs,event.rs,entity.rs,ids.rs,enums.rs,importance.rs,page.rs}`"
- **Category:** 5 — duplicated artifact
- **Defect:** both phases claim first creation of the same file. P04 gives it no content spec; P06 specifies the whole classifier table. An implementer following P04 literally creates an empty or guessed `importance.rs`, then P06's "Create" collides with it.
- **Why it bites:** P04's `Importance` enum work and P06's classifier are separate concerns, but the file list says otherwise; whoever executes P04 either writes a placeholder classifier (a faked implementation) or leaves an empty module that P04's own "no stubs" posture forbids.
- **Fix:** remove `importance.rs` from P04's Create list (P04 keeps `enums.rs`'s `Importance` variants only) and leave P06 as the sole creator, or make P06's entry "**Modify**".

### F6 — the `simulate_event` double gate has no test file and cannot be asserted from the builds P06 runs  [MEDIUM]
- **Where:** phase-06-event-engine-queries.md Success Criteria: "`simulate_event` is unreachable in a release build without the `devtools` feature *and* `developer_mode` enabled (test asserts the double gate)"; Implementation Steps 8: "gate the command with `#[cfg(any(debug_assertions, feature = "devtools"))]` **and** a `developer_mode` setting check"
- **Category:** 4 — unfalsifiable success criterion
- **Defect:** no test file in P06's Create list covers this (`query_service.rs`, `cluster.rs`, `importance_calm.rs`, `perf_scale.rs`), and no gate command runs it. Worse, the claim is unprovable from within the build it would have to run in: a test compiled with `debug_assertions` on satisfies the `cfg(any(...))` and therefore observes the command as **present**; the only build in which absence is observable is a release build without `devtools`, where the assertion code itself would have to be conditionally compiled to be meaningful.
- **Why it bites:** the phase's headline privacy/honesty guard (§87 — no synthetic row mistaken for real monitoring) ships as prose. A checkbox is ticked with nothing behind it.
- **Fix:** name the mechanism and the artifact: add `src-tauri/tests/dev_gate.rs` asserting (a) with `--features devtools`, `simulate_event` returns `Err(DeveloperModeDisabled)` while the setting is off, and (b) a build-level check that the command name does not appear in the generated `bindings.ts`/handler list when built without the feature (`cargo build --release` + `grep -c simulate_event` on the generated bindings, asserted `0`), and add both to the gate.

### F7 — 6h is roughly a third of this phase's real content  [MEDIUM]
- **Where:** phase-06-event-engine-queries.md front matter: `effort: 6h`
- **Category:** 8 — effort/scope mismatch
- **Defect:** the phase delivers five new service modules, `importance.rs` with a full escalation table, keyset cursor encode/decode, Rust-side clustering with a label template table plus expansion, a shared tokenizer + search ranking, the dashboard summary, a deterministic hand-rolled LCG generator producing realistic data across 15 categories with six profiles up to 1M rows and an entity-relationship mode, `simulate_event` for six event kinds, plus four test suites (including `EXPLAIN QUERY PLAN` and DST assertions) and a measured perf write-up. The synthetic generator alone — realistic names, relations, six profiles, deterministic seeding — is a day of work.
- **Why it bites:** P06 is the gate that unblocks all UI work (P07). A 3x underestimate here compresses either the generator's realism (making P07's and P15's fixtures unrepresentative) or the index/EXPLAIN work, which is exactly where F2 already bites.
- **Fix:** re-estimate to ~14–16h, or split the synthetic generator + `simulate_event` + perf harness into their own phase between P06 and P07 with the 10k budget recorded there.

### F8 — the search risk row implies a `LIKE` implementation, contradicting "over the P04 index"  [LOW]
- **Where:** phase-06-event-engine-queries.md Risk Assessment: "The inverted index is already the fallback; if it is the chosen path and still slow, cap candidate terms and add `search_terms(term)` prefix range scans instead of `LIKE`"
- **Category:** 9 — internal contradiction
- **Defect:** Requirements say `search_events` runs "over the P04 index", and P04 implements both paths behind `trait SearchIndex` (FTS5 when `ENABLE_FTS5`, else `search_terms(term, event_id) WITHOUT ROWID`). The risk row's "instead of `LIKE`" only makes sense if the first implementation queries with `LIKE`, which would bypass the index P04 built and break the 40 ms budget at 100k.
- **Why it bites:** an implementer reading the risk row as a design hint writes `LIKE '%term%'` first, ships it because 10k is fast enough, and P19 inherits a full-table scan.
- **Fix:** delete "instead of `LIKE`" and state the escalation inside the chosen path only: "if the `search_terms` path exceeds 40 ms, cap candidate terms per query and use `term >= ? AND term < ?` prefix ranges". Add a criterion that `search_service.rs` contains no `LIKE`.
